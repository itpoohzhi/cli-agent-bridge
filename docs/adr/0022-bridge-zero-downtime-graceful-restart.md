# 0022 — Бесшовный рестарт моста (Zero-Downtime & Graceful Restart) без срыва активных клиентских соединений

## Status

Approved (2026-11-02, пресет `analyst-teamlead`, Run ID: `bridge-seamless-restart-20261102`).
Расширяет: ADR-0005 (`0005-resilient-hub-lifecycle-and-detached-turns.md`), ADR-0017 (`0017-dsh-global-migration-unified-bridge-9882.md`).

## Контекст и проблематика

Пользователи DeepSeek Harness (DSH) и других клиентов сталкиваются с фатальным срывом активных ходов (`• This turn failed terminated TRANSPORT`) при любом перезапуске `cli-agent-bridge` (через `launchctl`, SwiftBar, скрипты развертывания).

Проведенный системный анализ выявил комплекс причин:
1. **[F-01] launchd SIGKILL через 5 секунд:** В `com.user.dsh-hub.plist` отсутствует ключ `ExitTimeOut`, из-за чего launchd применяет системный дефолт 5 с и принудительно убивает процесс по `SIGKILL`.
2. **[F-02] Принудительный interrupt в server.py:** `server.py` устанавливает `SHUTDOWN_GRACE_S = 4.5` и сразу вызывает `proc.interrupt_quietly()` для работающих потомков, обрывая генерацию.
3. **[F-03] daemon_threads = True:** Потоки клиентских HTTP/SSE-соединений создаются как daemon-треды и мгновенно уничтожаются рантаймом Python при выходе сервера без сброса буферов.
4. **[F-04] Отсутствие SO_REUSEPORT:** Без опции `SO_REUSEPORT` новый инстанс моста не может привязаться к `127.0.0.1:9882`, пока старый инстанс не освободил порт (`[Errno 48] Address already in use`).

## Архитектурное решение

### 1. AD-001: Включение SO_REUSEPORT на слушающем сокете
- В `server.py` в классе `Server(ThreadingHTTPServer)` переопределяется `server_bind()`:
  ```python
  if hasattr(socket, "SO_REUSEPORT") and is_so_reuseport_enabled():
      self.socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEPORT, 1)
  ```
- Параметр настраивается через переменную `BRIDGE_SO_REUSEPORT_ENABLED` (по умолчанию `"true"`).
- Это позволяет новому процессу запускаться параллельно со старым и сразу принимать новые входящие TCP-соединения.

### 2. AD-002: Разделение слушающего сокета и активных соединений (Drain Handoff)
- При получении сигнала `SIGTERM` / `SIGINT`:
  1. Старый сервер немедленно закрывает свой слушающий сокет (`server_close()`). Новые подключения клиентов автоматически маршрутизируются ядром ОС новому процессу моста.
  2. Активные HTTP/SSE-соединения старого процесса продолжают обслуживаться. Потоки соединений не прерываются.
  3. Старый процесс переходит в режим ожидания (`drain`) до завершения всех активных ходов (`_active_turn_count() == 0`) либо до истечения таймаута `DRAIN_TIMEOUT_S` (по умолчанию 110–120 с, конфигурируемо через `BRIDGE_DRAIN_TIMEOUT_S`).
  4. При истечении таймаута клиенту отправляется корректный terminal chunk (`finish_reason="stop"`) с сообщением о перезапуске, исключая необработанный разрыв сокета.

### 3. AD-003: Управление потоками соединений (Non-Daemon Worker Threads)
- Отказ от слепого `daemon_threads = True` для тредов обработки активных стримов: сервер регистрирует активные запросы и ожидает их завершения в фазе drain.

### 4. AD-004: Выравнивание LaunchAgent ExitTimeOut
- В `~/Library/LaunchAgents/com.user.dsh-hub.plist` устанавливается:
  ```xml
  <key>ExitTimeOut</key>
  <integer>180</integer>
  ```
- Это предотвращает преждевременный `SIGKILL` от `launchd` во время фазы плавного закрытия.

## Последствия (Trade-offs)
- **Плюсы:**
  - Полное устранение ошибки `TRANSPORT terminated` при плановом рестарте моста.
  - Нулевой downtime: новый процесс сразу готов обрабатывать трафик.
  - Чистое архитектурное решение в ядре хаба без правок вендорского ПО.
- **Минусы / Риски:**
  - Кратковременное удвоение потребления памяти в период смены процессов (пока старый завершает ход). Риск минимален благодаря изоляции процессов.
