# 0001 — Долгоживущий droid на чат (stream-jsonrpc) вместо `droid exec` на запрос

## Status

Accepted (2026-10-07). Формат: ADR-full — решение влияет на NFR (latency, ресурсы) и безопасность
(изоляция чатов, допуск образа), откатывается не одним действием (состояние на диске, receipt).

## Y-формулировка

В контексте моста DSH → Factory Droid, сталкиваясь с требованием, чтобы ход чата не платил за холодный старт
и replay всей истории (выигрыш ≥ 3,0 с на ход, REQ-002), мы решили держать по одному долгоживущему процессу
`droid exec --input-format stream-jsonrpc` на keyed-чат (с idle-гашением и `load_session` того же SID) вместо
запуска `droid exec` на каждый запрос и вместо общего демона на все чаты, чтобы получить быстрый resume с
изоляцией чатов на уровне процесса, принимая сложность учёта ресурсов (L/P/T), персистентности и допуска образа.

## Context

- Прежний мост запускал `droid exec` на каждый запрос и каждый раз переигрывал историю (холодный старт,
  потеря SID, нет `resumed`).
- Мост — stdlib Python, потоки, один процесс (`ThreadingHTTPServer`); внешний HTTP-контракт неизменен:
  пути, авторизация, `/health` ровно из 7 ключей, 6 моделей, таксономия ошибок 400/502/503 (без 507).
- Реальный droid (протокол 1.24x): `turnId` есть только у `agent_turn_completed` и равен id user-сообщения
  хода; ассистентские сообщения несут `parentId == turnId`; кадры содержат `factoryProtocolVersion`;
  `settings` read-back не возвращает `disableBuiltinSkills`/`autoRejectPermissionRequests`.
- DSH передаёт в запросе авторитетную историю и блок agent-instructions (KB/DW — копии канона ≤ 60 000 Б,
  WA/AB — до `maxBytes` профиля 106496); профили DSH и канон принадлежат владельцу.

## Decision drivers

1. Latency: повторный ход чата ≥ 3,0 с быстрее холодного (REQ-002); `resumed=1` на ходах ≥ 2 (REQ-001).
2. Изоляция: ни одно событие, сообщение или usage одного чата/хода не попадает в другой (тесты RW-006, изоляция resident-чатов).
3. Безопасность: нативные tools отключены по актуальному `list_tools`, настройки сверяются read-back, образ droid
   допускается по receipt (sha + протокол + политика tools + профиль настроек + пробы), ключ моста вырезан из env.
4. Ресурсы: ≤ `MAX_CONCURRENT` (4) процессов суммарно, память ограничена байтовыми бюджетами (8/4/10 МиБ), нет утечек слотов при любом отказе.
5. Эксплуатация: откат одним коммитом + перезапись receipt; сбой моста не оставляет «двойного user» в сессии droid.

## Considered options

- **Option A** — `droid exec` на запрос (как раньше). Просто и изолированно, но холодный старт и replay на каждый ход.
- **Option B** — по процессу `stream-jsonrpc` на keyed-чат, idle-гашение, restore через `load_session`.
- **Option C** — один общий демон droid, чаты мультиплексируются сессиями внутри процесса.

## Decision

Выбрана **Option B**.

### Y-rationale

B единственная даёт resume без replay при изоляции на границе процесса: чат — это процесс + SID + чистый Factory home.
C экономит процессы, но общий процесс делит состояние и сбой между чатами, а допуск образа и политику tools пришлось бы
доказывать для мультиплекса, которого у droid нет в протоколе. A не выполняет REQ-001/002.

## Pros and cons of options

### Option A — `droid exec` на запрос
- ✅ Полная изоляция ходов, нет персистентности, откат тривиален.
- ❌ Холодный старт и replay на каждый ход (нарушает REQ-002).
- ❌ Нет SID/`resumed` (нарушает REQ-001).

### Option B — процесс на чат
- ✅ Resume без replay, изоляция процессом, idle-гашение возвращает ресурсы, SID переживает рестарт.
- ✅ Все решения проверяемы fake-droid с реальным протоколом.
- ❌ Нужен учёт ресурсов L/P/T, персистентность (PENDING/READY/DIRTY), допуск образа, группы процессов.

### Option C — общий демон
- ✅ Минимум процессов.
- ❌ Общее состояние и сбой, нет протокольной поддержки мультиплекса, сложнее доказать изоляцию.

## Evaluation matrix

## Sensitivity check

Каждый вес по очереди изменён на −20 % и +20 % с перенормировкой (10 пересчётов): победитель всегда B
(диапазон B 3.89–4.00; A 3.52–3.79; C 3.32–3.48). Наименьший отрыв B от A — 0.10 при весе latency −20 % (3.89 против 3.79):
решение устойчиво, но чувствительно к весу latency; при снижении требования REQ-002 пересмотреть (Option A).

## Инварианты реализации (восстановимы без внешних материалов)

### Ресурсы L → P → T

- **L** — аренда чата (`Chat.lock`): один ход ключа за раз. Берётся первой; освобождается после terminal и checkpoint
  (запись READY), до доставки ответа клиенту.
- **P** — ёмкость процессов (`ProcPool`, cap `DROID_DSH_BRIDGE_MAX_CONCURRENT`=4; FIFO-очередь 900 с с keepalive 15 с).
  Включает resident, стартующие, эфемерные (title/без ключа/images) и закрывающиеся процессы; слот возвращается только
  после `waitpid`. Вытесняются только idle-чаты по LRU (SIGTERM → 2 с → SIGKILL группы).
- **T** — разрешение вычисления хода (`_slots`). Берётся последним, освобождается после terminal и checkpoint.
- Доставка клиенту не держит ни L, ни T: медленный клиент не блокирует следующий ход. Порядок строго L → P → T;
  при любом отказе (Popen, запуск потоков, конструктор хода, запись состояния) все взятые ресурсы возвращаются.

### Ход и изоляция

- Вывод удерживается до `agent_turn_completed` собственного хода: `turnId` терминала обязан быть непустым, не завершённым и
  равным id user-сообщения текущего хода (`active_turn`). Чужие/неизвестные/пустые терминалы, сообщения и дельты прежних ходов
  отбрасываются и не продлевают watchdog тишины. Набор завершённых turnId не вытесняется; предел 65536 → процесс заменяется
  (`retired`).
- Байтовые бюджеты: RPC-строка 8 МиБ, inbox 4 МиБ (запись ≥ 64 Б), текст хода 10 МиБ (дельта + итог блока = один раз);
  превышение — 502 `proxy_error`, процесс закрыт, слоты возвращены. Доставка срезами по 64 КиБ.

### Персистентность

- Запись чата `workspace/state/conversations.v1/chats/<2hex>/<sha256>.json` (schema 1, 0600/0700, только хеши):
  `state` ∈ PENDING | READY | DIRTY, `rec_rev` (CAS: расхождение — `StateConflict`), хеш-цепочка `head`/`n`, `cfg`, `sid`,
  `generation`, `restore_count`.
- Порядок хода: PENDING на диск → `add_user_message` → terminal → commit READY. Сбой записи PENDING — 502 до
  `add_user_message`; сбой commit READY — успех клиенту не выдаётся (502), процесс закрыт, чат DIRTY; после рестарта на диске
  PENDING, старый SID не продолжается — новая generation с replay.
- Restore после idle/рестарта — `load_session` того же SID (≤ 5 подряд, затем новая generation), затем проверка целостности
  служебных блоков (`restore_integrity`). Недоставленный/неполный ход, дрейф droid, расхождение истории — новая generation.
- `flock` на `.writer.lock` запрещает второй экземпляр; `children.json` + start-signature позволяют на старте добить только
  собственных осиротевших детей. Каталоги `state`/`runtime` принудительно 0700.

### Допуск образа (AD-010)

- Мост запускает droid только как `DROID_BIN=<образ из receipt>`. Receipt schema 2 пишет `tools/droid_image.py` атомарно после
  реальных проб (spawn / update / load в изолированном home): `image_path`, `image_sha256`, `protocol`, `tools_policy`
  (+digest), `settings_profile` (+digest), `probes`. На каждом spawn receipt перечитывается; любое расхождение — 503
  `launcher_unavailable`. Живой `factoryProtocolVersion` и каталог `list_tools` обязаны совпасть с квалифицированными
  (иначе 502 до `add_user_message`). `/health` показывает `ok:false` при невалидном receipt.

### Группы процессов и остановка

- Дети — лидеры собственных групп; закрытие сигналит группу независимо от лидера; сторож лидера добивает группу, если
  потомок держит pipe. SIGTERM моста: приём прекращается, дети закрываются параллельно в пределах 4,5 с, затем SIGKILL
  собственных групп.

### REQ-003 и охранник b_guard

- Гейт до spawn/add: блок «только канон» ≤ 60 000 Б; прочие блоки ≤ `maxBytes` профиля − 2048; проверяются все блоки во всём
  тексте. Контур b_guard в мосте (старт + период) переводит состояние в `unsafe`; тогда новые чаты с блоком получают управляемый
  отказ + alert, живые чаты не останавливаются.

## Consequences

- ✅ Повторные ходы идут без replay и холодного старта, SID переживает idle и рестарт.
- ✅ Ни один отказ не оставляет утёкших слотов/процессов/групп; все лимиты байтовые.
- ⚠️ Развёртывание — упорядоченная процедура (README, «Развёртывание»): без receipt ни один ход не обслуживается.
- ⚠️ Контур b_guard не пишет в `/health` (контракт 7 ключей): состояние видно в журнале.
- ⚠️ Spool больших ответов на диск не реализован: ответ ограничен бюджетом хода 10 МиБ и отдаётся срезами.
- 🔄 Живые стенды (keyed idle→restore с retention=long, изоляция двух resident-чатов, journal ≤ 60 000 Б, откат) — отдельный
  тяжёлый путь приёмки; в этом ADR не заявляются проверенными.

## Validation

- `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests` зелёный; регрессии cycle-2/cycle-3 — `tests/test_rpc_rework.py`,
  `tests/test_rpc_cycle3.py`.
- Живой журнал: `session_rpc path=restore resumed=1`, отсутствие `instr_guard_alert`/`droid_receipt_invalid` на старте.
- Пересмотр ADR: смена протокола droid (receipt перестаёт сходиться), изменение REQ-002, появление мультиплекса в протоколе droid.

## Rollback

Вернуть предыдущий коммит, перезаписать receipt прежней версией `tools/droid_image.py` (прежний код принимает только schema 1),
перезапустить мост. Формат записей чатов (schema 1) не менялся; сомнительные записи перестраиваются из истории запроса.
