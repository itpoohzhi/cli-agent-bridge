# Поддержка `prompt_cache_key` по мостам

Единый разбор — `core/chat_key.py` (`resolve_chat_key`). Контракт маршрута один:
невалидный ключ → `nokey`, запрос обслуживается как без ключа, **без `400`**.
Профилей валидности два (strict/lenient); lenient применяется только к muse и
фасаду как обратная совместимость.

`prompt_cache_key` по OpenAI-семантике — аффинность кэша префикса, его шарят
разные чаты; поэтому «принимает ключ» ≠ «ключ влияет на сессию». Честная матрица:

| Точка | Принимает `prompt_cache_key` | Уровень поддержки | Что именно делает | Почему так |
|---|---|---|---|---|
| `server.py` (фасад DSH) | да | `keyed-session` | ключ = идентичность логического чата: keyed-маршрут, горячий процесс на чат (lenient, `namespace`, предел 512) | прежнее поведение фасада сохранено — `server.py:7530-7537` |
| `bridges/muse-bridge` | да | `keyed-session` | ключ → `session_id` хода (lenient, без предела длины, значение как есть) | muse и до унификации использовал ключ как идентичность сессии; lenient+`NO_MAX_LEN` сохраняет её у существующих клиентов — `bridges/muse-bridge/server.py:2920-2924`, `:2999` |
| `bridges/agy-bridge` | принимается и **игнорируется** | `ignored` | сессия включается только по явным `x-dsh-chat-id` / `x-session-id` / `extra.chat_id` / `chat_id` | общий кэш-ключ склеил бы разные чаты в одну сессию; набор `SOURCES_SESSION_ID` — `bridges/agy-bridge/server.py:2864-2878`, `core/chat_key.py` |
| `bridges/claude-p-bridge` | да (плюс явные chat-id) | `log-only` | только корреляция в логе (`sha256`-дайджест); в argv и сессию не попадает | у `claude -p` нет API ключа кэша: кэш даёт сам CLI, метрики отдаются через `usage` (`prompt_tokens_details.cached_tokens`) — `bridges/claude-p-bridge/server.py:944`, `_wire_usage` |
| `bridges/opencode-zen-bridge` | да (плюс явные chat-id) | `log-only` | только корреляция в логе (дайджест); на апстрим не форвардится | у OpenCode/Zen сессия создаётся на каждый запрос, ключу некуда «прикрепиться» — `bridges/opencode-zen-bridge/server.py:8332-8337` |

## Уровни

- `keyed-session` — ключ определяет идентичность логического чата/сессии.
- `log-only` — ключ валидируется и пишется в лог как дайджест; на генерацию не влияет.
- `ignored` — ключ принимается без ошибки, но не используется (сессия — по другим источникам).

## Метрики кэша

Независимо от уровня поддержки ключа cache-usage (`usage.prompt_tokens_details.cached_tokens`)
отдаётся единообразно через `core/usage_wire.py` (`build_wire_usage`); арифметика кэша живёт
только там. Мусорные значения cache-read (отрицательные/нечисловые) на wire не попадают.

## Если нужно «keyed-session» для agy/claude-p/zen

Ключ там осознанно не идентичность. Менять уровень — только отдельной задачей с подтверждением
владельца (для agy — риск склейки чужих чатов; для claude-p/zen — нет API апстрима).
