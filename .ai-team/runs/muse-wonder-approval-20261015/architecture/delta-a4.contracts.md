# Нормативные контракты a4

## F-001(a3)

Необратимый общий барьер a4 (PF-a3-001): у запроса APPROVAL_SEEN защёлкивается сразу при получении approval/request, approval/requested или userInput/request, в том числе во время initialize/session/start/setup, ДО receipt, дедупликации и решения политики. ACTION_POSSIBLE для serve защёлкивается при самом раннем из этих событий, ДО первой попытки записи любого разрешающего approval/decide (approved либо approvedForSession, даже без предшествующего события) и ДО первого байта turn/start; exec — при успешном старте процесса с промптом. Разрешающий decide во время setup допустим только в том же процессе при allowAll, с теми же choices/лимитами/таймерами AD-002. ACK, -32051, terminal=false, ошибка/частичная запись, конец setup и смерть группы не сбрасывают ни один флаг. Эти флаги передаются Handler до возврата результата или исключения; агрегаты на запрос монотонны по всем попыткам. APPROVAL_SEEN или попытка разрешающего decide безусловно запрещают ЛЮБОЙ новый serve/exec (внутренний fallback, транзиентный и контекстный retry, обе области pre-action/observed-items). Не требуется доказательство фактически выполненного действия. Ошибка управляющего обмена после такого события терминальна по AD-002 даже до turn/start; если turnId ещё неизвестен, turn/cancel с выдуманным ID не посылается: доступный отказной decide в оставшемся счёте, иначе bounded ожидание/killpg. Setup-обработчик не продлевает SERVE_SPAWN_TIMEOUT_S и применяет min(CONTROL_WRITE_TIMEOUT_S, остаток setup/E); grace от локального защёлкивания обрезается общим дедлайном завершения AD-003. Тот же процесс может продолжиться успешно и послать первый turn/start; запрет касается переигрывания новым процессом.

## F-002(a3): бюджет

Бюджет a4 (PF-a3-002): t0 = time.monotonic() при приёме запроса Handler до очереди; D — АБСОЛЮТНЫЙ предел ВСЕГО запроса, включая очередь, вычисление, сериализацию, всю успешную либо ошибочную выдачу, закрытие соединения и bounded cleanup. D = t0 + min(TIMEOUT_S, REQUEST_CAP_S), REQUEST_CAP_S=1800 с (выбор ASM-013; при default TIMEOUT_S=1800 сохранён); большее операторское TIMEOUT_S не отодвигает D. При известных клиентских 1900 с [F-19]/EVD-016 запас не меньше 100 с, не используется для выдачи. E = D − FINISH_RESERVE_S (35 с), W = D − CLOSE_RESERVE_S (12 с). Очередь, все попытки и retry-паузы ограничены E, вся выдача и все её писатели — W; E..D резервируется для grace/уборки/выдачи/закрытия, но не доказывает доставку произвольного числа кадров. Успешная модель около E получает только остаток до W на финальную выдачу (максимум 23 с при default до затрат cleanup). Ни кадр, ни пауза, ни flush, ни keepalive, ни ожидание _wlock/остановки keepalive не продлевают W. Смена фаз и все входы в _wlock тоже bounded остатком до W. Независимый от писателя и _wlock надзор при достижении W атомарно останавливает выдачу, запрещает новые процессы, делает shutdown/close соединения без ожидания _wlock и прерывает все ожидания; уборка группы ограничена остатком до D (нового полного grace после W/D нет). CLOSE_RESERVE_S=12 с — явно выбранный continuable резерв по текущему worst-case _terminate_run 5+5+2, EVD-026; это не измеренный SLA ОС, ASM-013. Подтверждённая смерть освобождает слот ровно один раз до D; если подтверждения нет к D, соединение всё равно закрыто, слот в существующем карантине, новый процесс запрещён и отсутствие освобождения не маскируется успешным исходом. D не сдвигается при повторах или завершении модели. HTTP JSON non-stream использует тот же W/D и bounded запись, форма ответа не меняется.

## Выдача

Предел выдачи a4 (PF-a3-002): для любого вызова _sse_write в момент s единый локальный deadline L=min(s+LIVE_WRITE_TIMEOUT_S, W), LIVE_WRITE_TIMEOUT_S=3 с. Ожидание _wlock, sendall/write и flush используют один убывающий остаток до L (таймаут переустанавливается по остатку перед каждым блокирующим этапом, не по 3 с на этап); возвращается прежний socket timeout до освобождения замка. Этот предел действует на role, keepalive, live reasoning, финальный reasoning-хвост, tool_calls, КАЖДЫЙ content-кадр, finish_reason, usage, error и [DONE], без исключений. Все циклы сериализации/разбиения кадров, baseline-пауза 5 мс между content-кадрами и остановка/join keepalive проверяют W и прерываются надзором; нельзя начинать новый кадр/паузу при неположительном остатке, кадровый бюджет не обновляет W. keepalive допускается только OPEN, перед финальной выдачей останавливается в остатке до W. При истечении W либо L или частичном кадре запрос получает единственный локальный неуспешный исход delivery_deadline/client_gone, live и другие писатели остановлены, соединение закрывается; поздний успех модели игнорируется, повтор/fallback запрещены даже если ещё нет _content_started. После частично отправленного кадра или при нулевом остатке новый error/[DONE] не дописывается. Если ошибка известна раньше и полный корректный error+[DONE] успевает в оставшийся W, допустим один обычный ошибочный терминал; гарантировать его при аварийном обрыве нельзя. Успех существует только если ВСЯ конечная выдача, включая finish/usage и единственный [DONE], завершена до W; успешный локальный исход не фиксируется по завершению вычисления. При исчерпании бюджета результат может быть усечён закрытием соединения; отсутствие потери F обещается только для полностью доставленного успешного ответа. Полный текст и завершающий [DONE] после W не обещаются ни для читающего клиента, ни при расхождении snapshot. Нормальный путь сохраняет поля/порядок внешнего API. Резерв на 2 error-кадра не является доказательством доставки N content-кадров.

## Oracle F-001

T-R11 / T-A16 (новые тестовые контракты, ещё НЕ реализованы/не запускались; Coder сначала red на baseline a3, затем green): параметризовать setup initialize/session/start и approval/request с id / approval/requested без id. До turn/start сервер присылает approval, получает receipt где применимо и разрешающий decide, заглушка выполняет эффект-маркер ровно один раз и рвёт setup с [net-timeout]. Ровно один serve, exec-argv отсутствует, второго turn/start/нового процесса нет, эффект ровно один, локальный терминальный исход ровно один; при читающем клиенте и достаточном W один error+[DONE]. Проверить latch до первой записи decide при потере ack/частичной записи/ошибке receipt, повтор того же approval и -32051 флаги не сбрасывают. Матрица обеих retry_scope, а также кандидат контекстного retry с hard-threshold после approval: повтор запрещён при сохранении AD-005. Прямой путь allowing decide без inbound approval тоже защёлкивает до записи. Контроль: setup transient без approval/decide/turn/start по-прежнему допускает ограниченный serve retry и один fallback allowAll; denyUnmatched exec никогда не допускает. Тесты читают агрегат/счётчики и rpc.jsonl/process-argv, не доказывают инвариант одним grep.

Команда: `uv run --no-project --with pytest python -m pytest -q tests/test_muse_bridge_killpg.py -k 'Approval or TransientRetry'`

## Oracle F-002

T-L09 / T-R12 (новые тестовые контракты, ещё НЕ реализованы/не запускались; Coder red→green): модель успешно завершается около E, итог даёт N content-кадров и reasoning/tool_calls/finish/usage; детерминированный slow-steady клиент читает, КАЖДЫЙ кадр занимает меньше 3 с (в тесте пропорционально ужатого LIVE_WRITE_TIMEOUT_S), но сумма кадров+паузы превышает W. Синхронизированные fake monotonic clock и управляемый transport задают внешний oracle W/D от t0; на a3 без абсолютного output deadline запись проходит W (red), на a4: после W ни байта/flush/кадра/keepalive, shutdown/close наблюдён не позже W, все writers остановлены и группа мертва со слотом освобождённым один раз не позже D (green, bounded fake death). Повтор/fallback отсутствуют даже при нуле content-кадров, единственный локальный исход неуспешный, нет успешного finish/[DONE] после отсечки; error/DONE при обрыве не требуются, частичный кадр не дописывается. Повторить вариант: ожидание _wlock, затем write, затем flush каждый отдельно меньше 3 с, их сумма достигает L; общий бюджет не суммируется. Проверить паузы 5 мс, keepalive одновременно с финалом, join/phase-lock и blocked flush; независимый supervisor закрывает без захвата _wlock. Контроль N, успевающего до W: полный текст, finish/usage и ровно один [DONE], успех; default и TIMEOUT_S>1800 соблюдают cap с запасом 100 с, уменьшенный TIMEOUT_S сжимает D, очередь входит в t0. Неподтверждённая смерть к D: соединение закрыто, слот карантин, не false free/no retry. Дополнительно один реальный loopback slow-reader сценарий с малыми буферами подтверждает bounded закрытие без изменения clock; ОС scheduling tolerance фиксируется как измерение, не добавляется к production deadline.

Команда: `uv run --no-project --with pytest python -m pytest -q tests/test_muse_bridge_killpg.py -k 'LiveReasoning or TransientRetry'`
