### F-001 NON_BLOCKING — каскад `_get_setting` не соответствует заявленному в пакете порядку
`bridges/claude-p-bridge/server.py:149-158`: цикл идёт по `(name, fallback_name)` и для каждого ключа проверяет `os.environ`, затем `_DSH_ENV`. Поэтому `CLAUDE_P_BRIDGE_X` из файла `~/.dsh/.env` перебивает `BRIDGE_X`, заданный в реальном окружении процесса.
В пакете заявлен порядок `CLAUDE_P_BRIDGE_*` → `BRIDGE_*` → `default`, и файл по смыслу должен быть слоем ниже окружения. Сейчас окружение процесса проигрывает файлу для специфичного ключа.
Предлагаю собрать порядок явно: окружение по обоим ключам, затем файл по обоим, затем default.

### F-002 NON_BLOCKING — общий механизм настроек размещён в адаптере моста, а не в `core/`
`bridges/claude-p-bridge/server.py:106-171`: whitelist ключей, парсер `~/.dsh/.env` и каскад `_get_setting` / `_get_positive_float` живут внутри одного моста.
`server.py:394-406` читает только `os.environ` и файл `.env` не учитывает. Один и тот же параметр (таймаут) получает разный источник конфигурации в разных мостах.
Это противоречит принципу AGENTS.md п.5 «системное решение в `core/`, адаптеры — тонкие». Для других мостов, например zen, придётся копировать парсер.
Вынести хелпер в `core/` (например `core/settings.py`) с реестром ключей и использовать во всех мостах. Можно отдельным шагом.

### F-003 NON_BLOCKING — границы 1.0–300.0 в `parse_live_write_timeout` зашиты константами
`server.py:402`: диапазон `1.0 <= val <= 300.0` захардкожен, что нарушает AGENTS.md п.4.

Вынести границы в настройки или хотя бы логировать отвергнутое значение.
