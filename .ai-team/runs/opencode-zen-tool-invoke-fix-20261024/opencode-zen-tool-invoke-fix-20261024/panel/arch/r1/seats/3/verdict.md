#### 4. Неблокирующие замечания на реализацию и развитие (Visionary / Coherence Notes)
1. **Приоритет ошибки апстрима над `_BROKEN_BLOCK_NOTICE` в `_serve_json` (`AD-002`):** В `_stream_sse` ветка `failure` выполняется *до* эмиссии `_BROKEN_BLOCK_NOTICE`, поэтому при падении финальной попытки с `rc != 0` без вывода клиент получает ошибку, а не notice. В [`_serve_json`](file:///Users/aazhiry1/.dsh/bridges/opencode-zen-bridge/server.py#L3716-L3724) при подстановке `content = _BROKEN_BLOCK_NOTICE` стоит проверить `out.get("rc") == 0` (или `not out.get("err")`), чтобы отброшенный на первой попытке битый блок не замаскировал терминальный `502` финальной попытки под `200 OK`.
2. **Симметрия sink'ов внутри `opencode-zen-bridge`:** [`_stream_sse`](file:///Users/aazhiry1/.dsh/bridges/opencode-zen-bridge/server.py#L3176-L3178) делегирует Google-direct модели в [`_stream_google_sse`](file:///Users/aazhiry1/.dsh/bridges/opencode-zen-bridge/server.py#L3088), где создаётся отдельный `ToolCallParser(emit_content, emit_tool_call)` без обёртки, хотя `_serve_json` фильтрует Google-direct ответы через `_strip_broken_tool_blocks`. Вне скоупа инцидента `GLM-5.3-Flash`, но полезно иметь в виду для будущей унификации SSE/JSON.
3. **Горизонт дрейфа LLM мимо `_RAW_CALL_RE`:** Требование символа `{` в [`_RAW_CALL_RE`](file:///Users/aazhiry1/.dsh/bridges/opencode-zen-bridge/server.py#L512) оправдано защитой от ложного отрезания прозы с упоминанием `<tool_call>`, однако обёртка массива (`<tool_invoke>[{...}]</tool_invoke>`) или дублированный открывающий тег (`<tool_invoke><tool_invoke>{...}</tool_invoke>`) не совпадут с префиксом `_RAW_CALL_RE`. Текущий компромисс разумен (минимум ложных срабатываний `RISK-002`), а частоту таких случаев покажет лог `tool_call_unparsed`.
