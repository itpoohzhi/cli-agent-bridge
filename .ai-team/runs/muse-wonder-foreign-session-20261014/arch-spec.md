## 2. ADR-001.1 и ADR-001.2

### 2.1 ADR-001.1: единый источник лимита

- **Решение.** Окно модели хранится в одном месте: запись `ALLOWED_MODELS[model]`. Для двух wonder-моделей значение
  равно `400000`. Все остальные величины выводятся из него:
  - порог срабатывания `limit = window`;
  - целевой размер `target = limit * 4 // 5` (для 400000 это ровно 320000);
  - аварийный размер `retry_target = limit // 2` (200000).
- **Расхождение с брифом, фиксируется явно.** В коде ключ записи называется `context_length`, а не `contextWindow`
  (`server.py:73-78`, `:1710`); `contextWindow` существует только в YAML профилей DSH. Поэтому формула из брифа
  реализуется как `ALLOWED_MODELS.get(model, {}).get("context_length", 400_000)`, оформленная одним помощником
  `_context_limit(model)`. Второй ключ `contextWindow` в `ALLOWED_MODELS` не вводится: он создал бы второй источник
  истины. Значение по умолчанию `400_000` задаётся одной константой модуля.
- **Точки применения (4 значения, не больше).**
  1. `bridges/muse-bridge/server.py`: `muse-wonder-1.0`, `muse-wonder-full-1.0` -> `context_length: 400000`.
  2. `~/.dsh/bridges/muse-bridge/server.py`: зеркало. На 2026-10-14 побайтно совпадает с рабочим деревом репозитория
     (`diff -q` без вывода), включая незакоммиченные правки.
  3. `~/.dsh/profiles/desktop/cordis.patch.yml`: `contextWindow: 400000` у `id: muse-wonder-1.0` (строка 355) и
     `id: muse-wonder-full-1.0` (строка 369).
  4. `~/.dsh/profiles/web/cordis.patch.yml`: то же, строки 453 и 459.
- **Не трогать.** Записи `muse-spark-*` и все прочие провайдеры (десятки строк `contextWindow: 1048576`). Каталоги
  `~/.dsh/profiles/web.bak-*` (архивы). Профиль `headless`: `muse-bridge` в нём отсутствует (0 вхождений), проверить повторно
  перед выкатом.
- **Тест-регрессия.** `AllowedModelsSyncTest` (`tests/test_muse_bridge_killpg.py:1307`) сейчас жёстко проверяет
  `1048576`; обновляется первым (red), см. §6.

### 2.2 ADR-001.2: обязательный набор

Определения опираются на то, как `_messages_to_prompt` уже трактует роли: `system`/`developer` уходят в системный блок,
`assistant` и `tool` рендерятся как есть, любая прочая роль (включая отсутствующую) считается `user`.
Сообщение с пустым отрендеренным текстом (`_render_turn` вернул пусто) и не-словарь в расчёт не входят.

Обязательный набор M (в порядке неубывания приоритета отказа):
1. **Все** `system`/`developer` сообщения истории, в том числе поздние вставки.
2. Первый `user` (исходная постановка).
3. Последний `user` (текущий запрос). Если он совпадает с первым, сообщение учитывается один раз.
4. **Незавершённая единица ответа:** если последняя атомарная единица (см. §2.4) стоит позже последнего `user`
   (типичный цикл агента: `assistant(tool_calls)` + `tool`-результаты), она тоже обязательна. Без неё модель отвечает на
   вопрос, не видя результата, на который должна ответить. Это уточнение к брифу; оно вытекает из формата DSH и
   проверяется тестом T-13.

Порядок вывода сохраняет хронологию исходной истории. Системные сообщения по-прежнему выносятся в системный блок
существующей логикой `_messages_to_prompt`.

### 2.3 Пороги и гистерезис

- `est_total` > `limit` (400000) -> прунинг до `target` (320000). `est_total` ≤ `limit` -> запрос проходит без изменений,
  без маркера и без копирования (QS-02). Граница включительная: ровно `limit` не прунится.
- Запас до порога клиента 80000, до жёсткого лимита Meta (460800) 140800 токенов оценки.
- **Честное ограничение.** Мост без состояния. Если клиент не компактирует сам, история на каждом ходу растёт на
  новый ход, и начало хвоста сдвигается на этот же объём. Гистерезис гарантирует: (а) нет дребезга «пруним / не пруним»
  вокруг 400k; (б) неизменный префикс (системный блок, секция инструментов, первый `user`, маркер) побайтно стабилен и
  кэшируется; (в) после компакции на клиенте (он стартует около 400k) префикс хвоста снова стабилен. Стабильность
  префикса **хвоста** без компакции клиента не гарантируется. Квантование границы среза и серверное состояние сознательно
  отложены (deferred). См. RISK-002.

### 2.4 Инвариант атомарности инструментов

- **Атомарная единица.** `assistant`-сообщение с непустым `tool_calls` + все `role: "tool"` сообщения, чей
  `tool_call_id` совпадает с `id` любого из этих вызовов. Многовызовный ход (несколько `tool_calls` в одном
  сообщении) целиком одна единица. Каждое прочее сообщение является отдельной единицей.
- **Инвариант I-1.** В выходе прунинга нет `role: "tool"` без породившего `assistant` с таким же `tool_call_id` в
  том же выходе, и нет `assistant` с `tool_calls`, у которых часть ответов отброшена, а часть оставлена.
- **Осиротевшие `tool` во входе** (клиентская ошибка): при прунинге не попадают в выход; при проходе без прунинга
  остаются как есть (QS-02 требует дословности).
- Выбор хвоста идёт единицами от новейшей к старейшей, хвост непрерывный: остановка на первой единице, которая не
  помещается (без перескоков на более мелкие старые единицы).

### 2.5 Оценка токенов

- `est(text) = max(len(text) // 3, len(text.encode("utf-8")) // 3)`. Так как байтов не меньше символов, второй член
  всегда доминирует; формула записана в брифовой форме, реализация вправе считать только байты.
- В бюджет входят: системный блок вместе с обёрткой `[system]`, секция `_tools_section(tools, tool_choice)` целиком
  (`server.py:397`, JSON с `ensure_ascii=False`), разметка ролей (`User: `, `Assistant: `, `[tool result id] (name)`),
  разделители `\n\n`, маркер. Если инструменты не эмулируются, а `raw_tools` есть без system, учитывается
  `DEFAULT_SYSTEM_HINT`.
- Округление: к оценке каждой части прибавляется 1 токен, а итог всегда перепроверяется по **собранному** промпту:
  если `est(промпт) > target` (или `> limit` для жёсткой границы), хвост сокращается ещё на единицу. Тесты проверяют
  собранный промпт, а не промежуточную сумму.
- Консервативность имеет цену: для плотной кириллицы (2 байта на символ) оценка выше реальной токенизации, поэтому
  мост может прунить раньше, чем клиент считает окно исчерпанным. Принято осознанно (F-05); масштаб проверяется на
  живом ходе (ASM-004).

### 2.6 Отказ при превышении обязательного набора

Пусть `base = est(фиксированная часть) + est(M) + est(маркер)`, `cap` = `limit` для проактивного прунинга и
`retry_target` для retry.
- `base > cap` -> прунинг не может помочь. Мост **не запускает модель** и отвечает терминально (см. §3.3 и §4.3).
- Единица из п. 2.2/4 принимается, если `base + cost ≤ cap` (жёсткая граница, `target` здесь мягкая цель); иначе отказ.
- Остальной хвост добирается до `target` (проактивно) или `retry_target` (retry).
- Проактивный отказ происходит до `_sse_begin`, поэтому это обычный HTTP 502 JSON. Тело ответа: счётчики оценки и
  лимит; текст сообщений не включается.

### 2.7 Маркер и чистота функции

- Текст маркера: `[... earlier conversation turns compacted to stay within Muse context limit ...]`. Цифр лимита в
  тексте нет (единый источник).
- Маркер вставляется в каждый разрыв между соседними сохранёнными репликами, где отброшены единицы (разрывов не
  более двух: после первого `user` и перед хвостом, если последний `user` лежит раньше начала хвоста). Если отбрасывать
  нечего, маркера нет. Рендерится как нейтральная строка без префикса `User:`/`Assistant:` (внутренняя роль
  сообщения-заметки, обрабатываемая в `_messages_to_prompt`).
- Прунинг: чистая функция `(messages, limit, target, fixed_overhead_tokens) -> PruneResult`. Исходный список и словари
  не мутируются, результат собирается из ссылок на неизменённые сообщения. Детерминирован и идемпотентен: повторный
  прунинг своего выхода с теми же параметрами не меняет его.

## 3. ADR-001.3: аварийный auto-retry

### 3.1 Условие срабатывания (все пункты одновременно)

1. Попытка завершилась неуспехом: `out["rc"] != 0` и `out["state"] == "terminal_failed"`.
2. Подстрока `context compaction replacement still exceeds the hard threshold` найдена в **канале ошибки**
   (`out["err"]`, сырое значение до редакции), а не в `out["text"]`/`chunks`. Совпадение в обычном ответе модели retry
   не запускает.
3. Подстрока хранится одной константой модуля; на неё есть тест (T-17).
4. `context_retry_count == 0` (отдельный счётчик, не связанный с `NETWORK_RETRY_MARKER` и fallback `serve -> exec`).
5. Клиент не отключён (`not self._client_gone`), и контентные кадры ещё не отправлялись (§3.2).
6. Первая попытка очищена: `run.close()` выполнен, `run.dead_confirmed` истинно. Иначе retry не стартует, действует
   существующий карантин слота.
7. Прунинг для retry возможен: `base ≤ retry_target` (§2.6) и оценка нового промпта **строго меньше** оценки
   предыдущей попытки (иначе повтор бессмыслен: тот же промпт).
8. Не исчерпан суммарный дедлайн хода: `time.monotonic() - t_first_attempt < TIMEOUT_S`. Retry получает остаток, если
   сигнатура `execute()` позволяет; если нет, Coder фиксирует это в отчёте (принятый верхний предел 2×`TIMEOUT_S`).

Подделка: пользователь может подсунуть текст маркера так, что он отразится в `err`. Последствие ограничено одним повтором
(пункт 4), прочих побочных эффектов нет.

### 3.2 Граница «до первого контентного чанка»

- В текущем коде SSE открывается заранее (`_sse_begin`: заголовки, role-кадр, keepalive-комментарии), а все
  reasoning/tool_calls/content-кадры пишет `_send_sse` **после** завершения всех запусков (`server.py:1614`).
  Поэтому цикл retry целиком лежит до первого контентного кадра и между попытками клиенту уходят только keepalive.
- Защита на будущее: флаг `self._content_started` (выставляется под `_wlock` перед первой записью reasoning/tool/content
  кадра). Условие 5 §3.1 проверяет его. Если когда-нибудь появится реальный потоковый вывод, retry после первой дельты
  запрещён автоматически (повторять нельзя: нарушена идемпотентность потока).
- Между попытками нет ни `error`-кадра, ни `[DONE]`. Итог ровно один: успех либо терминальная ошибка.

### 3.3 Один повтор и терминальный исход

- `max_retries = 1`, цель среза `retry_target = limit // 2` (200000), промпт собирается из **исходных** `messages`, а не
  из уже прунённого списка.
- Повтор использует тот же слот (повторного `_slots.acquire` нет), добавляет `Run`/`ServeRun` в общий `runs` (чтобы
  `finally` закрыл обе попытки) и переключает `self._current_run`. Транспорт внутри попытки обычный: serve-first,
  fallback на exec допустим; сетевой retry допустим и не расходует контекстный счётчик. Вторая попытка с тем же маркером
  контекстный retry **не** запускает.
- Терминальный исход (повторный отказ, невыполнимый срез, превышение дедлайна, обязательный набор больше
  `retry_target`):
  - JSON: HTTP 502, `error.type = proxy_error`, `error.code = 502`;
  - SSE: один `error`-кадр и один `[DONE]` (существующий путь `_send` в фазе OPEN);
  - сообщение: `muse turn failed (rc=1, state=terminal_failed): context hard threshold exceeded after single compaction retry (est_tokens=<n>, target=<n>)`
    либо `...: mandatory context exceeds budget (est_tokens=<n>, limit=<n>)`. В сообщении только числа и константный
    текст.

## 4. ADR-001.4: безопасность, потоки, наблюдаемость

### 4.1 Потокобезопасность

- `self._wlock` (обычный `threading.Lock`, `server.py:1447`) защищает только запись в SSE-сокет (`_sse_write`).
  Прунинг и сборка промпта выполняются в потоке запроса до `_sse_begin` и повторно между попытками **без** замков;
  ни один метод, берущий `_wlock`, не вызывается из прунинга. Тест T-11 фиксирует: во время прунинга `_wlock` не
  захвачен.
- Состояние попытки (`context_retry_count`, `_content_started`, предыдущая оценка) живёт в локальных переменных
  обработчика запроса и в экземпляре `Handler` (по одному на соединение); глобальных изменяемых структур не добавляется.

### 4.2 Секреты и тела сообщений

- Тела отброшенных и сохранённых сообщений, tool arguments, multipart-текст и промпт в лог и диагностику не пишутся.
- Каждая строка лога и каждое диагностическое сообщение проходит `_redact_secrets` (`server.py:177`).
- Отражённый промпт убирается для **обеих** попыток: список `reflected_prompts` накапливает промпт каждой попытки;
  замена `[REDACTED]` и обход `messages` (существующая логика `server.py:1877-1955`) выполняются до усечения до 500
  символов и во всех приёмниках: лог, JSON, SSE.
- Детектор retry читает сырой `err` только для сопоставления с константой; в лог и ответ уходит уже отредактированный
  текст.

### 4.3 Структурное событие прунинга

Одна строка `_log` на каждое срабатывание прунинга и на каждый retry:

```
context_prune rid=<8 hex> model=<id> reason=<proactive_prune|hard_threshold_retry|refused_mandatory|refused_retry> attempt=<1|2> limit=<n> target=<n> est_before=<n> est_after=<n> msgs_total=<n> msgs_kept=<n> msgs_dropped=<n> mandatory_est=<n> overhead_est=<n> method=bytes_div_3
```

- Только числа и константные слова. `rid` генерируется на запрос (`uuid4().hex[:8]`), связывает строки обеих попыток.
- Заголовок ответа вроде `X-Muse-Context-Pruned` и переопределение лимитов через env в этот MR не входят (deferred).

## 5. Границы и контракты

- Внешний вход: OpenAI `/v1/chat/completions`, JSON и SSE. Поля запроса и формат ответа успеха не меняются.
- Внешний выход, изменённый контракт: `context_length` двух wonder-моделей в `/health` и `/v1/models` = 400000
  (QS-03).
- Новый внутренний контракт: ошибка 502 с двумя новыми константными текстами (§3.3).
- Зависимости: только stdlib. Новых пакетов и файлов конфигурации нет.

## 8. Риски и допущения (сводка; полный список в пакете)

- RISK-001: оценка `bytes//3` не совпадает с токенизатором Meta -> тяжёлый путь и сравнение с `usage`.
- RISK-002: хвост без компакции клиента сдвигается каждый ход -> кэш хвоста мимо; префикс стабилен. Принято.
- RISK-003: потеря реплик, молчаливая для пользователя -> маркер для модели и строка `context_prune` для оператора.
- RISK-004: открытые слоты со старым окном -> перезапуск слотов.
- RISK-005: retry при нераспознанной смене формата ошибки Meta -> константа и тест; сбой даёт обычный 502.
- ASM-003 (OPEN, continuable): Muse CLI/serve не держит серверного состояния сессии, которое делало бы урезание входных
  `messages` бесполезным (замечание Визионера). Проверка: тяжёлый путь, `usage.prompt_tokens` после прунинга.
- Вопросы владельцу (не блокируют): Q-001 имя ключа `context_length`; Q-002 `muse-spark-*` остаются на 1048576;
  Q-003 способ перезапуска моста.
