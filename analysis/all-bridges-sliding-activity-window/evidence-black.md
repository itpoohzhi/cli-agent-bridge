# Evidence Black — Риск-анализ сквозного Sliding Activity Window (все мосты)

Шляпа: Чёрная (INV-02). Дата: 2026-11-02. Симптом: отсутствует (превентивная доработка).
Объект: `bridges/agy-bridge/server.py`, `bridges/opencode-zen-bridge/server.py`, `bridges/claude-p-bridge/server.py`, `core/watchdog.py`.
Основание: as-is факты `evidence-white.md` [W-01..W-08] + сверка кода в рабочем дереве ветки `feature/bridge-resilience-patterns`.

Шкала: **BLOCKER** — без митигации не принимать; **MAJOR** — митигация обязательна в этой же поставке; **MINOR** — принять с тестом/наблюдением.

## Опорные факты (as-is, проверено в коде)

- F-1 `claude-p-bridge/server.py:602–610` — цикл `run.q.get(timeout=POLL_INTERVAL_S)`: на `queue.Empty` только keepalive (`: keepalive\n\n`) и `continue`; ни idle-таймера, ни safety cap; слот `_slots` (`BoundedSemaphore(MAX_CONCURRENT=8)`, `:209`) освобождается только в `finally` `_run_once` (`:685`).
- F-2 `claude-p-bridge/server.py:522–526` — `_acquire_slot` ждёт до `QUEUE_TIMEOUT_S` (900 с, `:179`).
- F-3 `opencode-zen-bridge/server.py:1609–1654` — `_StdoutReader.lines(deadline, idle_s, on_idle)`: `last_activity` сбрасывается на **любую** строку stdout; абсолютный `deadline` проверяется и на Empty, и после получения строки (`:1648`).
- F-4 `opencode-zen-bridge/server.py:4895–4909` и `:8448–8464` — `first_token_timeout` считается от `prompt_send_start`/`attempt_start` (`FIRST_TOKEN_TIMEOUT_S`, `:1943`), `stall_timeout` — от `last_token_at` (`STALL_TIMEOUT_S=60`, `:1946`); две независимые реализации одной логики (HTTP-путь и CLI-путь).
- F-5 `agy-bridge/server.py:6128–6163` — две ветки: при `extended_timeout_enabled` скользящее окно по `last_producer_activity_ts` (обновляется `note_producer_activity`, `:5294–5300`, источники stdout/transcript) + cap `effective_max_timeout_s`; без флага — настенный `run.started + TIMEOUT_S` (1800 с). `first_token_timeout` в обеих ветках — от `run.started`.
- F-6 `core/watchdog.py:476–491` — `last_activity_ts` продлевается по `metrics.has_progress` = `cpu_delta` **или** `new_descendants` (CPU-время группы процессов, не полезные чанки); safety cap — `BRIDGE_SAFETY_CAP_S` → `DROID_DSH_BRIDGE_SAFETY_CAP_S` → 3600 с (`:384–390`).
- F-7 `agy-bridge/server.py:274` — `idle_timeout_s = min(idle_timeout_s, cap)`: клампинг idle к cap уже есть в agy, в остальных мостах нет.

## Реестр рисков

### 1. Границы / контракты (OpenAI API и SSE)

- [B-01] **MAJOR** — Смена `finish_reason`/типа ошибки при обрыве. Сейчас клиенты (DeepSeek Harness, хаб `:9882`, `smoke_models.py`) различают `timeout` / `first_token_timeout` / `stall_timeout` / `idle_timeout` (agy `:6820–6824`, zen `:6616–6617`, `:7575–7576`, `:9183–9184`, `:9597–9598`). Унификация под одно `idle_timeout`/`absolute_cap` ломает маршрутизацию фолбэков (zen FALLBACK_DECISION_TABLE, `:2089–2097` классифицирует именно `first_token_timeout/stall`). Митигация: таблица соответствия «старая причина → новая» с сохранением старых строк в `error.type`; новые причины — только добавлением.
- [B-02] **MAJOR** — Терминальный кадр при срабатывании cap посреди стрима. Если cap/idle срабатывает после частичной выдачи, мост обязан закрыть стрим валидно: финальный chunk с `finish_reason`, затем `data: [DONE]` (инвариант структурного DONE из коммита `20e8cb5`). Риск: новый путь выхода из цикла (особенно в claude-p, где его сейчас нет — F-1) вернёт `state(...)` без обрамления → у клиента обрыв без DONE / незакрытый `tool_calls`-аргумент. Оракул: L2-тест «idle посреди `tool_calls` → валидный JSON аргументов или явная ошибка, затем `[DONE]`».
- [B-03] **MINOR** — Изоляция `<Think>`: при сдвиге дедлайна по reasoning-чанкам нельзя менять канал выдачи; любые сервисные сообщения о продлении/предупреждении («ещё жив») — только SSE-комментарием `: …` или в `reasoning_content`, никогда в `content` (инвариант L2 AGENTS.md).
- [B-04] **MINOR** — Имена env. Новые `BRIDGE_IDLE_TIMEOUT_S`/`BRIDGE_SAFETY_CAP_S` не должны молча перекрывать существующие пер-мостовые (`OPENCODE_ZEN_BRIDGE_STALL_TIMEOUT_S`, `AGY_BRIDGE_*`, `CLAUDE_P_BRIDGE_*`, `DROID_DSH_BRIDGE_SAFETY_CAP_S`). Цепочка приоритета должна быть явной и одинаковой (пер-мостовая → общая → дефолт), как `_chain_float` в agy.

### 2. Безопасность (зацикливание, утечка ресурсов)

- [B-05] **BLOCKER** — Бесконечное продление по паразитной активности. Если в «полезную активность» попадут: собственные keepalive моста (claude-p `: keepalive` раз в 15 с, agy `keepalive_s=15`), SSE-комментарии апстрима, `server.heartbeat` (zen `:2425`), пустые/whitespace-дельты, повторяющиеся статус-строки — окно не закроется никогда, и единственной защитой остаётся cap. В zen это уже так: `lines()` сбрасывает `last_activity` на **любую** строку stdout (F-3). Митигация: сброс таймера только по непустым `content`/`reasoning_content`/`tool_calls` после нормализации (`StreamNormalizer`/`_ContentArbiter`), а не по сырому байту/строке; разделение `last_input` vs `last_upstream`, как в `passthrough_adapter` [W-08].
- [B-06] **BLOCKER** — Отсутствие safety cap там, где окно становится «вечным». После перехода на sliding window любой мост без абсолютного cap получает неограниченное время хода. Сейчас claude-p не имеет ни idle, ни cap (F-1); agy без флага `extended_timeout_enabled` опирается на настенный `TIMEOUT_S` — если его заменить на sliding без cap, теряется последний предохранитель. Требование: cap обязателен в каждом мосту, включён по умолчанию, `cap > idle` с валидацией (клампинг как agy `:274`), значение ≤ `T_REQ_BUDGET_S` клиента.
- [B-07] **MAJOR** — Ложная активность CPU в `core/watchdog.py` (F-6). Процесс в busy-loop (зависший CLI, бесконечный ретрай внутри агента, GC-шторм Node) даёт `cpu_delta > 0` и вечно продлевает окно без единого чанка клиенту. Если мосты переиспользуют `TurnWatchdog` как источник активности — это прямой обход п. B-05. Митигация: CPU/descendants — только сигнал «жив» для grace, не для сдвига дедлайна полезного стрима; два разных таймера.
- [B-08] **MAJOR** — Зомби/сироты при срабатывании нового пути обрыва. Новый выход по idle/cap обязан вызывать тот же kill-путь, что и client_gone (`_kill_group` claude-p `:340–344`, `_stop_proc` zen, killpg agy `:2808`). Риск: `return state("idle_timeout")` из цикла чтения без убийства группы → процесс CLI продолжает жечь токены/квоту провайдера. Оракул: тест «idle сработал → `os.killpg` вызван, PGID мёртв ≤ grace».
- [B-09] **MINOR** — Злонамеренный/дефектный апстрим может удерживать соединение отдачей 1 токена раз в `idle−ε` секунд (slow-drip). Sliding window по определению это пропускает; ограничитель — только cap и, опционально, минимальная скорость (токенов/мин). Зафиксировать как принятый риск либо добавить `BRIDGE_MIN_RATE` (выкл. по умолчанию).

### 3. Целостность данных (потеря/дублирование чанков)

- [B-10] **BLOCKER** — Гонка «дедлайн истёк ↔ чанк уже в очереди». В zen `lines()` после получения строки проверяется `last_activity > deadline` и строка **отбрасывается** (`:1648–1650`); в agy проверка cap идёт до вычитки очереди. При переносе на sliding window легко получить потерю последнего чанка/терминального события (`done`/`result` с usage). Требование: при срабатывании idle/cap — бесконечно не ждать, но дочитать уже буферизованное (`get_nowait` до пустоты, как в ветке `_done.is_set()` `:1630–1636`) и только потом закрывать.
- [B-11] **MAJOR** — Дубли при retry после idle. zen и agy делают повторные попытки (Retry Budget, `MAX_TOTAL_SPAWNS`, `:3014–3063`). Если idle наступил после частичной выдачи и мост ретраит, клиент получит повтор уже отданного префикса. Требование: после `delivered=True` (zen `:4902`, `:4908`) ретрай запрещён либо идёт через `_ContentArbiter` с инвариантом `_scan` (`text == candidate` / `startswith`) — без ослабления.
- [B-12] **MAJOR** — Сдвиг дедлайна из потока producer'а без синхронизации. В agy `last_producer_activity_ts` пишется под `_activity_lock` (`:5297`), но читается в цикле через `getattr` без замка (`:6137`). Для float в CPython это атомарно, однако при добавлении составного состояния (ts + kind + счётчик) неатомарное чтение даст рассинхрон (окно «продлено», а kind старый → неверная причина обрыва). Требование: единый объект окна с `snapshot()` под замком, общий для всех мостов (V2 `core/streaming_watchdog.py`).
- [B-13] **MINOR** — Сброс окна на `tool_calls`-дельтах: аргументы инструмента часто идут одним большим куском после долгой паузы генерации; если `first_token_timeout` не учитывает reasoning/tool-фазу (agy `no_first_event` считает только `got_event`/transcript), длинная генерация аргументов оборвётся до первого видимого чанка. Учитывать в «первом событии» все три класса.

### 4. Обратная совместимость (тесты с жёсткими таймаутами)

- [B-14] **MAJOR** — Тесты, проверяющие ровно текущие таймауты. Ссылки на `*TIMEOUT_S` в тестах: `tests/test_bridges_speedup_resilience.py` (49), `bridges/opencode-zen-bridge/tests/test_realtime_reasoning.py` (51), `tests/test_agy_bridge_resilience.py` (32), `tests/test_muse_bridge_killpg.py` (17), `tests/test_muse_adapter.py` (10), `tests/test_rpc_lifecycle.py` (8), `tests/test_hub_scaling.py`, `tests/test_bridge_http.py` (по 6) и др. Тесты, ожидающие обрыва по настенному лимиту при **непрерывном** потоке, станут красными по смыслу — их нельзя «чинить» подгонкой; каждое изменение ожидания — с обоснованием в PR (старое поведение было дефектом). Риск противоположный: тест «срабатывает таймаут» может стать зелёным по другой причине (cap вместо idle). Оракул: ассерт на конкретную причину, а не только на факт обрыва.
- [B-15] **MAJOR** — Тайминг-флаки. Sliding-логика с реальными `time.monotonic()`/`sleep` в тестах (`_STDOUT_POLL_S=0.25`, `POLL_INTERVAL_S=1`) даёт недетерминизм под нагрузкой CI (полный `uv run pytest -q`, параллельные воркеры). Требование: инъекция часов (`clock=` как в zen `self._clock`, `:2680–2705`) во все новые окна; L1-тесты — на фейковых часах без `sleep`.
- [B-16] **MINOR** — Дефолты. Если дефолтное поведение станет «sliding вместо wall», это смена runtime-поведения → по канону нужен фичефлаг GigaRC `*_ENABLED` с `false` по умолчанию (agy уже следует этому через `extended_timeout_enabled`, F-5). Без флага — откат только деплоем.

### 5. Ресурсный конверт (сокеты, семафоры `max_concurrent`)

- [B-17] **BLOCKER** — Удлинение удержания слота семафора. Слоты малы: agy `MAX_CONCURRENT=4`, zen `2` (`:547`), claude-p `8`. Sliding window по замыслу удлиняет живые ходы (до cap 3600 с вместо 1800/300/120 с) → время удержания слота растёт до 2–30×; очередь `QUEUE_TIMEOUT_S=900` (F-2) и admission zen (`wait_timeout_s`, `max_waiters`) начнут массово отвечать «bridge busy». Требование: расчёт конверта (RPS_peak=50 из research-plan × p95 длительности хода / слоты) до выбора дефолтного cap; метрика занятости слотов в `/health`.
- [B-18] **BLOCKER** — Медленный клиент блокирует апстрим и держит слот. Запись в сокет синхронная (`self._emit` → `wfile.write`); при переполненном TCP-буфере медленного клиента поток моста блокируется в `write`, цикл чтения не крутится, idle/cap **не проверяются** вовсе, а очередь `run.q` растёт без ограничения (неограниченный `queue.Queue` → память). Слот держится до таймаута сокета (`HTTP_TIMEOUT_S=300`, claude-p `:188`) или навсегда, если он не выставлен на запись. Требование: таймаут на запись сокета ≤ idle, ограниченная очередь producer→consumer с политикой (backpressure/kill), проверка дедлайна не зависит от успешности `write`.
- [B-19] **MAJOR** — Утечка слота на новом пути выхода. Добавляемый `return` по idle/cap обязан проходить через `finally: _slots.release()` (claude-p `:685`) и `_cid_release` (agy `:3388`, `:5183`). `BoundedSemaphore` при двойном `release` бросит `ValueError` — значит, нельзя добавлять release в новые ветки «на всякий случай». Оракул: счётчик свободных слотов до/после 100 ходов, завершившихся idle, cap и client_gone, — равен `MAX_CONCURRENT`.
- [B-20] **MAJOR** — Keepalive vs proxy idle. Если продление окна перестанет сопровождаться SSE-keepalive на стороне клиента (или keepalive станет реже idle прокси/LB — Cordis, nginx, `:10815`), клиентская сторона порвёт соединение раньше моста, а мост продолжит держать апстрим и слот (до обнаружения `client_gone`, которое в claude-p проверяется раз в `POLL_INTERVAL_S` только между событиями). Требование: `keepalive_s < min(client_idle, proxy_idle)` и проверка `client_gone` на каждой итерации, включая ветку с данными.
- [B-21] **MINOR** — Ожидание в очереди admission не должно сдвигаться активностью (W-05 предлагает продлевать `QUEUE_TIMEOUT_S` при «активности в очереди»): это позволит ожиданию длиться неограниченно, пока соседние ходы активны. Очередь — строго абсолютный лимит; sliding — только для фазы стрима.

### 6. Асимптотика hot-path (`time.monotonic()` на чанк)

- [B-22] **MINOR** — Стоимость вызова. `time.monotonic()` на macOS/Linux — vDSO/`mach_absolute_time`, порядка 30–80 нс в CPython; при 50 RPS × ~100 чанков/с на стрим (≈5·10³ вызовов/с) это <1 мс CPU в секунду — в бюджет `T_budget ≤ 1ms` на запрос укладывается с запасом в 3–4 порядка. Само по себе не блокер; замер обязателен (`timeit` в L1, порог 1 µs на чанк для всей логики окна).
- [B-23] **MAJOR** — Реальный hot-path риск — не часы, а замок и ветвления вокруг них. Захват `threading.Lock` на каждый чанк (как `_activity_lock` agy `:5297`) при конкуренции producer/consumer под GIL даёт микросекундные паузы и contention; плюс `getattr`, `_new_flag(...)` (чтение GigaRC/конфига, agy `:6130`, кэш `_cfg_checked_at` `:3060`) **в каждой итерации** цикла. Требование: флаг и политика вычисляются один раз на ход; сдвиг дедлайна — одна запись float без замка (атомарна в CPython) либо батч-обновление не чаще шага поллинга.
- [B-24] **MINOR** — Дублирование вычислений: zen вызывает `on_idle()` на каждую строку (`:1651–1654`) — watchdog с несколькими сравнениями и логированием на каждый чанк; при больших фреймах (`S_frame_max=32MB`, мелкая нарезка строк) это O(N строк) лишней работы. Проверка дедлайна достаточно с частотой поллинга (`_STDOUT_POLL_S`), а не на каждую строку.
