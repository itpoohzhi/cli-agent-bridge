# Handoff системного анализа для архитектора (REQ-ZEN-TIMEOUT-01)

## 1. Контекст и цель требования
- **REQ-ID:** `REQ-ZEN-TIMEOUT-01`
- **Проблема:** В рамках ADR-0021 (B-4) для `deepseek-v4.1-flash-free` был введен жесткий дедлайн 25 с на промптах >8192 байт. Это привело к преждевременному обрыву запросов с кодом HTTP 504 / SSE error (13.5% отказов в логах [F-04]), когда модель начинала генерацию на 15–20 секунде, но не успевала завершить весь вывод к 25-й секунде.
- **Целевое состояние:** Заменить монолитный таймаут на раздельные:
  1. `ttft_timeout = 25.0 с` (до получения первого токена/события контента). Если за 25 с нет ни одного токена — честный 504 Gateway Timeout.
  2. `idle_timeout = 15.0 с` (максимальная пауза между последовательными токенами). Если стрим замер более чем на 15 с — таймаут зависания.
  3. `total_timeout = 180.0 с` (или `TIMEOUT_S`) — верхняя планка на всю попытку.

## 2. Архитектурные драйверы (Architecture Drivers)
- **ADR-01 (Availability):** Ликвидация ложных 504/502 на тяжелых аналитических промптах >8 КБ.
- **ADR-02 (Fail-Fast):** Сохранение быстрого отсечения реально зависших запросов (TTFT > 25 с).
- **ADR-03 (Configurability):** Полная настраиваемость через переменные окружения: `BRIDGE_ZEN_TTFT_TIMEOUT_S` (25.0), `BRIDGE_ZEN_IDLE_TIMEOUT_S` (15.0), `BRIDGE_ZEN_TOTAL_TIMEOUT_S` (180.0).

## 3. Границы влияния (Callers / Callees)
- **Компонент:** `bridges/opencode-zen-bridge/server.py`
  - Функция `_zen_execution_timeout` (или новая структура `_ZenTimeouts`)
  - Функция `_serve_one_attempt` (цикл `while time.monotonic() < deadline:`)
  - Обработчик `_send` / `_sse_error` (выставление 504 при `exit_reason == "timeout"`)
- **Тесты:** `tests/test_bridges_speedup_resilience.py`

## 4. Конверт HL-ENV/v1
- `concurrency`: до 128 параллельных запросов
- `ttft_budget`: 25.0 с
- `idle_budget`: 15.0 с
- `total_budget`: 180.0 с
- `fail_mode`: Fail-Closed (504 при превышении TTFT или Idle)
