# Системный анализ: Внедрение паттерна «Скользящее окно активности» (Sliding Activity Window) в скилы AI-SDLC

- **Дата:** 2026-11-02
- **Автор:** System Analyst (`gemini-4-argon-high`)
- **Статус:** APPROVED FOR SKILLS INTEGRATION

---

## 1. Проблематика: Антипаттерн «Прибивание по настенным часам» (Wall-Clock Killing)

### 1.1. Симптомы и инциденты
1. В интерфейсе DeepSeek Harness агент падал с ошибкой:
   `• This turn failed pi-ai stream idle timeout after 300000ms TIMEOUT` при выполнении длительных дисковых и сетевых операций.
2. При вызове моделей через passthrough (`gemini-3.8-flash` через `agy-bridge`) агент падал с ошибкой:
   `• This turn failed upstream stream failed PI_AI_ERROR` ровно через 420.0 с (`DEFAULT_TOTAL_TIMEOUT_S = 420.0`).
3. В ядре моста процессы в состоянии `S` (interruptible sleep в ожидании сокета/диска) прибивались через 300 с, так как `cpu_delta == 0.0`.

### 1.2. Системная первопричина в существующих скилах
В существующих скилах разработки (`ai-sdlc`, `orchestrate-*`, `aisdlc-gcge`) детально описаны стоп-коды для пулов соединений (`C-MULT`), лавинных запросов (`S-HERD`), перегрузки CPU (`H-CPU`) и изоляции отказов (`R-BULK`).
**Однако отсутствовал явный стандарт для управления временем жизни стримов и длительных агентских задач:**
- Разработчики устанавливали жесткие статические таймауты (`timeout=N`, `deadline = start + total_s`), которые слепо обрывали активный поток при достижении настенного времени, полностью игнорируя факт того, что поток **активен, производит токены и совершает полезную работу**.
- Отсутствовало разграничение между **таймаутом бездействия (Idle / Silence Timeout)** и **аварийным потолком безопасности (Safety Hard Cap)**.

## 2. Новый архитектурный паттерн: `Sliding Activity & Progress Window` (`L-LIVE`)

### Инвариант 1: Разделение простоя и общего времени (Decoupling Idle Silence from Total Duration)
- **Запрещено:** Использовать единственный статический `timeout` для операций с потенциально неограниченным объемом полезных данных (генерация LLM, чтение стримов, выполнение сложных агентских сценариев).
- **Обязательно:** Разделять:
  1. `idle_timeout_s` — допустимое время полного отсутствия активности/токенов (тишина). По умолчанию 120–300 с.
  2. `safety_cap_s` — абсолютный аварийный потолок (предохранитель от бесконечного зацикливания/repetition loop). По умолчанию 3600 с (1 час).

### Инвариант 2: Скользящий дедлайн по активности (Progress-Driven Extension)
- При получении **каждого полезного кванта данных** (токен `content`, `reasoning`, аргументы вызова инструмента, строка лога процесса):
  ```python
  last_progress = time.monotonic()
  # Дедлайн неактивности непрерывно сдвигается вперед:
  idle_deadline = last_progress + idle_timeout_s
  ```
- Соединение/процесс завершается по таймауту **только при выполнении условия:**
  $$\text{now} - \text{last\_progress} > \text{idle\_timeout\_s}$$
  и пока не превышен аварийный $\text{safety\_cap\_s}$. Если данные поступают — операция живёт столько, сколько требуется задаче.

### Инвариант 3: Осведомленность о состоянии процесса в ОС (OS State & IO Awareness)
- При отсутствии новых токенов в сокете watchdog обязан проверять состояние группы процессов в ОС (`ps -o state=`).
- Состояния ядра `S` (sleep/wait), `D` (disk sleep/uninterruptible), `I` (idle kernel thread), `U` квалифицируются как ожидание ввода-вывода (IO-wait).
- Для таких процессов предоставляется `io_wait_cap_s` (например, 900 с / 15 минут) с логированием, без преждевременного `SIGKILL`.

### Инвариант 4: Активный прогресс-хартбит (Active Progress Heartbeat)
- Если клиентский парсер отбрасывает комментарии протокола (`: keepalive\n\n`), мост обязан периодически инжектировать распознаваемые клиентским парсером активные data-кадры прогресса (например, дельты reasoning с пробелом или статусом), сбрасывающие сторожевой таймер на стороне клиента.

## 4. Рекомендации по реализации в `cli-agent-bridge`

1. **В `adapters/passthrough_adapter.py`:**
   - В `_TimedSseReader.readline()`: связать проверку дедлайна с `last_progress`. Если `last_progress` обновляется — `self.deadline = min(self.safety_cap, time.monotonic() + self.limits.idle_timeout_s)`.
   - Внедрить активный data-heartbeat при паузах апстрима.
2. **В `server.py`:**
   - В `_execute()`: проверять `time.monotonic() - run.last_progress > effective_silence_s`, а не настенный `TIMEOUT_S`, пока не достигнут `SAFETY_CAP_S`.
